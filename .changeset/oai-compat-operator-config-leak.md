Stop openai-compat callers from reading the operator's private global `CLAUDE.md`. An openai-compat caller is an arbitrary user, but the claude backend spawned to serve it loaded the operator's user-global `~/.claude/CLAUDE.md`, so asking the model what was in its context returned that file verbatim — along with `$HOME`, and with it the OS account name. The openai-compat isolation cwd did not cover this: it keeps *project* CLAUDE.md and project settings out, while the user-global file loads regardless of cwd. The openai-compat spawn now passes `--setting-sources project`, which drops user-global settings. Verified end-to-end that the file contents and home path no longer appear, that the sandbox guard still applies (it rides the separate `--settings` channel, and a spawn under this flag is still denied a write to `$HOME`), and that OAuth still works — unlike `--bare`, the only other switch that drops CLAUDE.md but which is API-key auth only. Scoped to openai-compat; plain A2A tasks run on the operator's own behalf and keep their context. The operator's account email stays in claude's injected context and is not removable via any flag — it is suppressed at the prompt layer instead: the openai-compat system prompt now closes with an operator-privacy clause telling the model the account metadata belongs to the operator, not the caller, and to decline to disclose it. Unlike the injected date (where such an instruction fails), this holds — suppressing PII disclosure aligns with the model's training rather than fighting it; verified 13/13 including adversarial probes (exact-value demand, operator impersonation, verbatim context dump). Prompt-level, so not a hard guarantee.
